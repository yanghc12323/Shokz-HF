# 耳廓工程分析桌面软件 PRD 与使用说明

> 文档状态：工程 Alpha；适用平台：Windows 10/11 本机离线运行。
> 目标：将既有耳廓分析 CLI 封装为可审计的中文工程软件，同时保持同一输入、同一参数下的分析核心与 CLI 一致。
> 本文区分“当前已实现”和“发布验收目标”，不将规划功能表述为已交付功能。

## 1. 产品边界

软件用于对耳廓三维网格执行既有分析流程：输入规范化、patch remesh、raw/repaired/salvaged QC、整耳 Weld、GPA 对齐、固定参考耳对齐（可选）、PCA 与平均耳。它在本机创建项目副本和隔离运行目录；不会上传数据，也不会修改用户选择的原始输入文件。

第一版不提供 region table 或边界控制点的图形编辑、距离/面积/角度量测、PDF/Word 报告、云端协作或并发多任务。

## 2. 角色与基本原则

| 角色 | 主要操作 | 约束 |
|---|---|---|
| 常规使用者 | 新建项目、导入、校验、一键分析、查看结果 | 仅可调整少量运行参数；配置内容在项目文件夹中维护。 |
| 专家使用者 | 选择已有失败 attempt，执行可用的 Weld/对齐/PCA 恢复 | 只能使用通过完整性校验的上游产物；每次重跑均为新 attempt。 |
| 维护者 | 更新代码/依赖、构建 EXE、查看日志 | 发布前必须通过 CLI 一致性测试和完整回归。 |

所有正式桌面运行都遵守以下原则：

1. 一个项目同一时间只允许一个本地运行进程。
2. 每次全流程运行使用新的、隔离的 `artifacts` 输出根目录，绝不写入 legacy `output/` 共享目录。
3. 父 attempt 的产物只读；恢复运行不得覆盖它。
4. QC 拦截是有效结论，不是“界面错误”；每个拦截样本都应保留机器原因、中文解释和证据入口。

## 3. 启动、更新与构建

### 3.1 使用已构建软件

在发布目录中双击：

```text
dist\耳廓工程分析\耳廓工程分析.exe
```

默认推荐“目录版”发布，因为 PyVista/VTK 依赖较大，启动和问题定位都优于单文件版。

### 3.2 开发环境启动

```powershell
cd "D:\YHC\人头项目\.worktrees\desktop-engineering-app"
python -m pip install -r requirements-desktop.txt
python -m desktop_app
```

### 3.3 从源码更新软件

每次修改 Python 代码、UI、内置字体、配置模板或依赖后，必须重新构建；重新生成的 `dist` 内容就是更新后的软件。

```powershell
cd "D:\YHC\人头项目\.worktrees\desktop-engineering-app"
$env:QT_QPA_PLATFORM='offscreen'
python -m pytest tests -q
powershell -ExecutionPolicy Bypass -File scripts\build_desktop.ps1
```

如果程序正在运行，先关闭 EXE 再构建，避免 Windows 锁定发布文件。构建单文件版：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build_desktop.ps1 -OneFile
```

`build/`、`dist/` 和 PyInstaller 生成的 `.spec` 文件属于构建产物，不应作为业务源码修改或提交。

## 4. 项目与数据目录

用户选择的项目根目录必须为空。软件在其中创建如下结构：

```text
<项目根目录>/
  project.json                         # 项目名称与 schema 版本
  inputs/
    clean_mesh/                        # 从来源复制的 *.ply
    landmarks/                         # 从来源复制的 *_landmarks.csv
    config/
      region_table.csv                 # 运行配置副本
      edge_control_points.csv          # 运行配置副本
  runs/
    run-<时间戳>/
      attempts/
        attempt-001/
          control.json                 # 全流程暂停/取消控制
          desktop_state.json           # UI 可见状态
          events.jsonl                 # 结构化进度事件
          artifacts/                   # 本次全流程唯一输出根
            manifest.json
            pipeline_batch_summary.csv
            pipeline_run_summary.csv
            pipeline_run.log
            ...分析阶段产物...
        attempt-002/                   # 恢复运行的 child attempt（如有）
          recovery.json
          desktop_state.json
          artifacts/
            manifest.json
            ...仅本次阶段重跑产物...
```

### 4.1 输入文件要求

| 输入 | 必需 | 格式/命名 | 校验行为 |
|---|---:|---|---|
| 网格目录 | 是 | `*.ply`，样本名如 `T001_L.ply` | 复制至 `inputs/clean_mesh/`。 |
| 地标目录 | 是 | `*_landmarks.csv`，如 `T001_L_landmarks.csv` | 与网格按 sample tag 配对。 |
| 区域表 | 是 | CSV，至少含 `region_id`、`resolution` | 复制并检查必需列。 |
| 边界控制点 | 是 | `edge_control_points.csv` | 复制并检查文件存在。 |

源文件在复制后不再是分析运行的直接依赖；软件只使用项目目录中的副本。因此，若需要更换输入或配置，应新建项目，或在确认可追溯性后由维护者直接维护项目 `inputs/config/` 中的副本。

## 5. 默认交互路径

```text
新建项目
  → 导入输入副本
  → 自动校验
  → 运行参数
  → 一键全流程分析
  → 运行监控（暂停/继续/取消）
  → 自动载入结果复核
```

### 5.1 新建项目

1. 打开“项目”页。
2. 填写项目名称。项目名称仅用于区分分析批次，不会修改原始样本文件名。
3. 点击“浏览文件夹…”，选择一个空的工作目录；目录路径由软件自动填入，不能手工编辑。软件会在该目录中建立项目、复制输入并保存运行记录和结果。
4. 点击“创建项目”。
5. 软件生成 `project.json`，随后进入自动校验页。

若目录已存在且非空，创建会被拒绝，避免把项目文件与未知内容混合。

### 5.2 导入与自动校验

1. 在“导入数据”页填写网格目录、地标目录、区域表和边界控制点路径。
2. 点击“导入并自动校验”。
3. 软件复制符合命名规则的文件到项目目录，随后立即运行校验。

校验发现 ERROR 时，运行参数页和一键分析均不可进入。典型阻断原因包括：

- 缺少网格目录或地标目录；
- 某个样本只有 PLY 或只有 landmark CSV；
- 区域表缺少 `region_id` 或 `resolution`；
- 缺少边界控制点配置。

校验通过时，软件自动进入“运行参数”。当前 UI 已实现路径输入与导入，但文件选择对话框、项目最近记录和覆盖导入策略仍是后续增强项。

### 5.3 运行参数

当前可从界面调整的参数为：

| 参数 | 默认值 | 含义 |
|---|---:|---|
| 最大 Salvage 未映射比例 | 0.35 | 超过该比例时 Salvage 不具备后续准入条件。 |
| 最大 Salvage 退化比例 | 0.015 | Salvage 面退化的上限。 |
| PCA 累积解释方差 | 0.75 | PCA 保留主成分的累计解释方差阈值。 |
| 固定参考耳 | 空 | 可选 sample tag；填入后运行固定参考耳对齐/PCA 分支。 |

参数页不允许编辑 region table 或边界控制点内容。配置需要变更时，维护项目副本中的 CSV 并重新校验；为保证可追溯性，推荐新建项目再导入新配置。

### 5.4 一键全流程分析

点击“一键开始分析”后，桌面端创建新的逻辑运行和 `attempt-001`，以子进程调用既有：

```text
scripts/run_full_pipeline.py
```

桌面端传入项目内的网格、地标、区域表和新的 `--output-root`，并附加：

- `--event-log <attempt>/events.jsonl`
- `--control-path <attempt>/control.json`

因此，桌面端不重新实现 remesh、Weld、对齐或 PCA 算法；它只封装现有 CLI 的输入、运行控制和产物索引。未传桌面专用参数时，CLI 原有命令与默认行为保持不变。

### 5.5 运行监控与状态

监控页显示当前 attempt 状态及最近一条 JSONL 事件（阶段、事件类型、样本 tag）。全流程的运行状态包括：

| 状态 | 含义 | 可操作项 |
|---|---|---|
| `RUNNING` | 正在运行 | 暂停、取消。 |
| `PAUSE_REQUESTED` | 已请求暂停，等待安全检查点 | 取消。 |
| `PAUSED` | 已在安全检查点暂停 | 继续、取消。 |
| `CANCELLED` | 已取消 | 查看已保留证据；必要时专家恢复。 |
| `FAILED` | 运行错误 | 查看 manifest/log；必要时专家恢复。 |
| `COMPLETED` | 正常完成 | 自动进入结果复核。 |

暂停/取消只对完整 pipeline 的安全检查点有效。专家阶段脚本当前不提供同等的文件检查点协议，不应把其运行误认为可安全暂停。

## 6. 输出、结果复核与导出

完成运行后，软件读取 `manifest.json`、`pipeline_batch_summary.csv`、Weld QC、alignment QC、PCA 输入清单，并只索引 manifest 声明且位于当前 `artifacts/` 内的路径。任何越出 attempt 根目录的 manifest 路径会被拒绝。

### 6.1 样本级状态与拦截解释

结果复核显示以下状态：Raw/remesh、Salvage、Weld、对齐和 PCA。PCA 状态会显示“纳入”“未纳入”或“拦截”。常见机器原因及中文解释：

| 机器原因 | 界面含义 |
|---|---|
| `MISSING_MESH` | 缺少原始网格。 |
| `MISSING_LANDMARKS` | 缺少对应地标文件。 |
| `salvage_not_pass` | Salvage 未通过，后续整耳阶段被拦截。 |
| `weld_not_pca_ready` | Weld 或边界 QC 未达到 PCA 准入条件。 |
| `alignment_not_pass` | 整耳对齐 QC 未通过。 |
| `pca_error` | PCA 阶段执行失败。 |

未知机器原因不会丢弃，会以原文保留，供维护者追溯。

### 6.2 三维图层

可用时，结果工作台支持加载：

- 原始网格；
- 修复网格；
- Salvaged 网格；
- Weld 整耳；
- PCA 平均耳。

VTK 视图支持鼠标旋转、滚轮缩放、右键平移、重置视角，以及按 `region_id` 请求区域高亮。没有产物的图层会禁用；平均耳不可用时会明确提示 PCA 未完成或未产生平均耳。无图形桌面/离屏环境会给出渲染不可用提示，而不启动不稳定的 VTK 窗口。

“导出”在第一版指打开、复制或交付既有 CSV、PLY、OBJ、STL、PNG、manifest 和日志；不生成 PDF/Word 报告。

## 7. 专家模式与失败恢复

专家模式的目标是“从可验证的已完成上游继续”，而不是绕开 QC。

1. 选择一个失败或取消的父 attempt（当前专家面板已经具备可用阶段展示和启动逻辑；运行记录中的 attempt 选择器仍待补齐）。
2. 软件检查父 manifest 声明的路径是否为相对路径、是否仍位于父 `artifacts/` 下、目录是否真实存在。
3. 仅启用满足条件的阶段：
   - Weld：父 attempt 的 `salvaged_dir`；
   - 对齐：父 attempt 的 `weld_dir`；
   - PCA：父 attempt 的 `aligned_dir`，并同时要求 Weld 输出可用。
4. 启动后创建 `attempt-002`（或下一个序号），生成 `recovery.json` 与新的 `desktop_state.json`。
5. child attempt 的 `recovery.json` 记录父 attempt、来源阶段、父 manifest SHA-256、来源路径。
6. 阶段进程退出码为 0 才写 `COMPLETED` manifest；非零退出写 `ERROR` manifest 和错误信息。

恢复不会自动合并回父 attempt，也不会覆盖父 attempt 的任何文件。

## 8. CLI 兼容与验收

CLI 仍是分析基线，示例：

```powershell
python scripts/run_full_pipeline.py
python scripts/run_full_pipeline.py --skip-remesh-qc
python scripts/run_full_pipeline.py --reference-sample T076_L
```

桌面端把同一组参数转换为 CLI 参数并调用同一脚本。当前已具备“桌面命令可被 CLI 解析且配置映射一致”的自动测试；发布验收还应补齐同一小样本下 manifest、批次状态和关键产物哈希逐项一致的端到端测试。

发布前最低检查：

```powershell
$env:QT_QPA_PLATFORM='offscreen'
python -m pytest tests -q
powershell -ExecutionPolicy Bypass -File scripts\build_desktop.ps1
```

## 9. 当前版本限制与发布前待办

以下能力仍未达到最终交付状态，应在正式发版前完成或在发布说明中明确排除：

1. 运行记录页尚未提供项目内 attempt 列表和专家模式的父 attempt 选择器。
2. 专家恢复完成后仅生成阶段 manifest；尚未将其自动聚合为完整全流程结果复核。
3. “暂停”仅保证完整 pipeline 的协作式安全检查点，恢复阶段脚本没有暂停协议。
4. GUI/CLI 已有参数映射测试，但尚未完成真实小样本的逐产物哈希一致性验收。
5. PyInstaller 构建需要在真实 Windows 图形会话中完成 EXE 启动、一次小样本分析和三维交互的人工冒烟验证。

## 10. 支持与故障排查

| 现象 | 首先检查 | 处理建议 |
|---|---|---|
| 无法进入运行参数 | 自动校验页 | 修复所有 ERROR；重点确认配对文件和两个配置 CSV。 |
| 一键分析立即失败 | `<attempt>/artifacts/manifest.json`、`pipeline_run.log`、`events.jsonl` | 确认输入副本和项目配置；保留 attempt 后再使用专家恢复。 |
| 结果图层不可用 | 结果侧栏提示与 manifest `outputs` | 检查该阶段是否完成、文件是否仍在当前 artifacts 内。 |
| PCA 被拦截 | 样本级 `reason`、Weld/对齐 QC CSV | 不应手工绕过；修复上游 QC 或使用允许的恢复阶段。 |
| EXE 构建失败 | `build/` 日志、Python 依赖版本 | 先运行 `python -m pip install -r requirements-desktop.txt`，再执行完整测试与构建。 |
